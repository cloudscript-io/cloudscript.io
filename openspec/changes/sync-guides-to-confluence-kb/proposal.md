# sync-guides-to-confluence-kb — proposal

## Why

The Jira Service Management help centre for project CUS (cloudscript.atlassian.net/helpcenter/CUS) is being branded and published, and the intention is to switch on the JSM virtual service agent (Rovo) so that simple customer questions are answered in chat without an agent. The virtual service agent answers only from the project's knowledge base, which is a linked Confluence space; JSM's other attachable sources are SharePoint and Google Drive folders, and there is no option to point it at a public website. The user guides already exist and are maintained in exactly one place, this repository (the app page under `apps/<slug>/index.html` is the guide by convention, CLAUDE.md §3), so any knowledge base that is maintained by hand will drift from the website the first time an app ships a release. This change makes the website the single source of truth and mirrors the guides into a Confluence knowledge base space automatically on every push to `main`, so a release updates the help centre and the virtual agent with no manual step.

## What Changes

- **A GitHub Actions workflow** (`.github/workflows/kb-sync.yml`) that runs on push to `main` when a guide or registry file changed (`apps/**/index.html`, `_data/apps/*.yml`, `scripts/kb-sync/**`), and on manual dispatch with a `dry_run` input. It is the first workflow in this repository and is independent of GitHub Pages (Pages keeps building the site natively; the workflow never touches the deploy).
- **A Node script** (`scripts/kb-sync/`, no runtime dependencies beyond a pinned HTML parser) that, for every registry entry with `status: live`, extracts the guide body from the app page, converts it to Confluence storage format, and upserts one page per app in the knowledge base space. Pages are found by a stable marker (a page property holding the app slug), not by title, so renaming an app does not orphan its page.
- **Idempotent, change-only writes.** The script stores a content hash in a page property and skips the update when the hash is unchanged, so a push that touches nothing in a guide creates no new Confluence version and no notification noise.
- **Extraction boundary.** The synced body is the guide proper: the lede and introductory paragraphs, then every `<h2>` section up to but excluding the `Legal` section (legal pages stay on the website and are linked from a fixed footer paragraph on each synced page). Trust badges, inline `<style>`, scripts and analytics are stripped. Relative links and image sources are rewritten to absolute `https://www.cloudscript.io/...` URLs; images are referenced from the website, not uploaded as attachments, so a screenshot replaced on the site updates in Confluence on the next sync without a re-upload.
- **Retired apps.** A registry entry that leaves `status: live` (or is deleted) causes its knowledge base page to be moved under an `Archived guides` parent and prefixed `[Archived]`, never deleted, so nothing the virtual agent has already cited disappears silently.
- **Not changing:** the website content, layouts or URLs; the Marketplace registrations; the existing Atlassian Resources Confluence space (an internal summary layer, out of scope and not the target); the JSM project configuration itself (linking the space as the knowledge base and enabling the virtual agent are one-off manual steps by Natasha, listed in tasks as verification gates, not automated).

## Capabilities

### New Capabilities

- `kb-sync`: source selection from the registry, the extraction boundary, HTML to storage-format conversion rules, page identity and idempotent upsert, triggers, credential handling, archive-on-retire, and dry-run behaviour.

### Modified Capabilities

- none (no existing capability specs in this repository; this change creates `openspec/`).

## Impact

- **Code:** `.github/workflows/kb-sync.yml`; `scripts/kb-sync/{sync.mjs,extract.mjs,convert.mjs,confluence.mjs}`; `scripts/kb-sync/package.json` (own lockfile, pinned versions, installed only by the workflow, so the site build is untouched); `tests/kb-sync/` with per-app fixtures and storage-format goldens; `README.md` and `PROJECT_STATUS.md` gain a section describing the sync and its one-off setup; `.gitignore` gains `scripts/kb-sync/node_modules/`.
- **Existing users:** none of the website's readers are affected. Help centre customers gain searchable articles that match the website; once Natasha enables it, the virtual agent answers from the same text.
- **Affected teams:** Natasha (one-off setup: Confluence space, service account, GitHub secrets, JSM knowledge base link, virtual agent switch-on); Patrick (review of the workflow and the least-privilege token); the Cowork help-centre work (the help centre's Resource Tiles block and the virtual agent depend on this space existing).
- **Adversarial security review.** Data flows one way, from a public repository to Confluence; nothing is read from Confluence except the sync's own pages, and nothing from Confluence flows back into the site, so a compromised or mis-edited Confluence page cannot alter the website. Credentials: a dedicated service account (not Natasha's or Patrick's admin identity) holding a scoped Atlassian API token with only `read:page:confluence`, `write:page:confluence` and the space-property scopes, and granted space permissions only on the knowledge base space; the token lives in GitHub Actions secrets, is passed to the script by environment variable, and the script never logs request headers or bodies that carry it. Blast radius if the token leaks: an attacker can rewrite pages in one public knowledge base space and nothing else; rotation is a one-line secret change. Supply chain: the workflow pins actions by full commit SHA and the script pins its single dependency exactly, with `npm ci` against the committed lockfile. The workflow has `permissions: contents: read` only and uses a concurrency group so two pushes cannot race and interleave writes. Content: everything synced is already public on the website, so the space adds no disclosure, but it is worth stating that the virtual agent will quote from it verbatim, which is the reason the extraction boundary excludes the legal sections (their authoritative copies must stay the dated website pages). Prompt-injection surface: the guides are authored by Cloudscript, but the script must never execute or evaluate page content, only transform it; this is a plain HTML transform with no templating of untrusted strings into code.
- **Test plan.** Unit tests over the extractor and converter with one fixture per live app and a golden storage-format document per app, asserting the extraction boundary (lede kept, `Legal` excluded, badges and `<style>` stripped), absolute URL rewriting, well-formed XML output, and stable hashing. A dry-run test that runs the full script against the fixtures with a mocked REST layer and asserts the exact sequence of intended writes, including the skip path when hashes match and the archive path when a registry entry is not live. Live verification, gated on Natasha having created the space and secrets: `workflow_dispatch` with `dry_run=true` printing the intended writes for all seven apps; then a real run; then each page read back through the REST API and compared to the golden; then a second real run proving zero writes; then one deliberate guide edit pushed to `main` proving a single-page update. Finally, with the space linked to CUS, one article opened from the help centre search and one question put to the virtual agent, recorded in a run report.
